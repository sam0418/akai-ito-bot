# 001 — VCA-Lite：長期記憶能否改善翻譯

## 背景

正式版的 Gemini 翻譯器只帶最近 10 段對話當上下文，而且上下文存在 `CacheService`，6 小時後就會消失。
在 30 句的日常對話測試裡，Gemini 已經 30/30 正確（見 `src/DialogueTest.js`）。
但那份測試只需要短期上下文；跨天的指代、兩人之間固定的稱呼和梗，現在的設計看不到。

VCA（Vector-based Cognitive Architecture）的主張是：不靠換更大的模型，而是靠充實上下文來得到記憶的連續性。
本實驗把 VCA 的記憶設計移植成輕量版，去掉所有人格與情緒元件，只保留「記憶與組裝上下文」，最後交給 Gemini 翻譯。

## 假說

- **H1（Profile 層）**：從過去對話整理出的關係檔案（稱呼、事實、固定說法），能讓需要跨天記憶的翻譯更正確。
- **H2（Episodic 檢索）**：檢索過去相似的對話當範例，能讓重複出現的說法翻得更一致。
- **H0（虛無假說）**：在最近 10 段上下文之外加入記憶，不會帶來可測量的改善。

如果條件 B 在長期記憶題上沒有明顯勝過條件 A，就不做第二階段，並在「結論」記錄原因。

## 方法

### 實驗條件

| 條件 | 上下文 | 對應正式版 |
|---|---|---|
| A（基準） | 同一天內最近 10 段 | 現行 `gemini` 翻譯器（上下文 6 小時過期） |
| B | A + Profile 層 | 第一階段 |
| C | B + Episodic 檢索 | 第二階段 |

三個條件使用相同的模型與相同的翻譯指示；除了上下文，其他都不變。評估時 `temperature` 設為 0。

### 測試資料

`fixtures/long-memory.json`：多天的虛構對話情境。前幾天的對話只用來建立記憶，最後一天的 `probe` 才計分。
每個 probe 都設計成**沒有前幾天的資訊就容易翻錯**，例如：

- 指代：幾天前提過「我妹妹要來」，今天說「她到了」，「她」是誰？
- 固定稱呼：兩人給某隻貓取的綽號，之後要一致地翻成同一個詞。

### 評估指標

1. **probe 通過率**：每個 probe 的 `mustAny` / `mustNot` 檢查。
2. **人工語意檢查**：逐句確認意思與語氣。
3. **延遲**：每次翻譯的時間（正式版的預算是 5 秒，其中打包等待約 3 秒）。
4. **成本**：每次請求的 token 數（免費方案有每分鐘上限）。

### 執行

在 `akai-ito-bot` 資料夾執行（需要 Node 20 以上）：

```powershell
$env:GEMINI_API_KEY = "你的金鑰"          # 只在這個終端機視窗有效，不會存檔
node experiments/001-vca-lite/run.mjs --condition A
```

| 參數 | 說明 |
|---|---|
| `--condition A\|B\|C` | 實驗條件 |
| `--model <id>` | 覆寫模型（預設用 `src/Config.js` 的設定） |
| `--repeat <n>` | 整組測試重複 n 次，並列出每題的穩定度 |
| `--scenario <id>` | 只跑單一情境 |
| `--pace <毫秒>` | 每次請求的間隔，預設 4500（免費方案有每分鐘上限） |
| `--mock` | 不呼叫 API，只檢查流程 |

翻譯指示、詞彙表與模型設定直接從 `src/` 載入，所以實驗和線上版本完全一致；評估時 `temperature` 固定為 0。
結果存到 `runs/<條件>-<時間>.json`。

### 移植自 VCA 的設計

| VCA | VCA-Lite | 處理方式 |
|---|---|---|
| Profile／Semantic Memory | 關係檔案（JSON，可人工檢查與修改） | 保留 |
| Episodic Memory + 向量檢索 | 以 Gemini embedding 檢索過去對話 | 保留（第二階段） |
| 遺忘策略介面 | 事實不衰減，一般對話隨時間降權 | 保留 |
| getSoulPrompt | 組合翻譯 prompt | 改寫 |
| Emotion Inertia Engine、人格行為、LiveContextPlugin | — | 移除：翻譯工具不能有自己的情緒或個性，也不能加入原文沒有的資訊 |

### 隱私

關係檔案與檢索內容都會送到 Gemini API。免費方案的內容可能被 Google 用來改進產品。
真實對話只放在 `data/`，不提交；用真實資料跑出的結果也不提交。

## 結果

### Run 1：條件 A（基準）— 2026-10-18

模型 `gemini-3.5-flash-lite`，temperature 0。平均延遲 817 ms，平均 prompt 397 tokens。

| 情境 | 原文 | 條件 A 譯文 | 自動評分 | 人工判讀 |
|---|---|---|---|---|
| S1 指代 | 她昨天晚上到了 | 昨日の**お父さん**の夜に着いたよ | ❌ | ❌ **嚴重錯誤**：不知道「她」是誰，憑空編出「爸爸」 |
| S1 指代 | よかった！疲れてないかな？ | 太好了！不知道會不會很累？ | ❌ | ✅ 省略主詞，沒有誤指 |
| S2 綽號 | 今日も親分いたよ | 今天**老大**也在喔 | ❌ | ❌ 讀起來像在說人（上司），失去「那隻貓」的指涉 |
| S2 綽號 | 親分有沒有變更胖 | お姉ちゃん、おやぶんまた太った？ | ❌ | ✅ おやぶん就是親分；句首多叫了一聲お姉ちゃん |
| S3 約定 | 取れたよ！来週の金曜日 | 搶到啦！下週五 | ❌ | ✅ 「搶到」符合很難訂的語境 |
| S4 暗號 | 充電したい… | 想充電… | ✅ | ✅ 保留字面，兩人自己懂 |

自動評分 1/6，人工判讀 4/6。

**觀察**

1. 第一版的評分標準太依賴特定字詞，把語意正確的譯文判成錯誤（S1 第二句、S2 第二句、S3）。
   已依語意修訂 `fixtures/long-memory.json` 的評分條件，每個修訂都附上 `note` 說明理由；原始結果保留在 `runs/`。
2. 真正因為缺少長期記憶而翻錯的有兩類：
   - **指代無先行詞時會幻覺**：「她」在當天對話裡沒有對象，模型編出了原文沒有的人物。這是最危險的錯誤。
   - **自取的名稱會被一般化**：「親分」被翻成一般名詞「老大」，失去兩人之間的指涉。
3. 跨天的計畫（S3）與暗號（S4）在條件 A 下語意已可接受，記憶對這兩類的邊際效益可能有限。
4. 「お姉ちゃん」仍有被多加的傾向，屬於翻譯指示的問題，與記憶無關，另外處理。

**處理（Run 1 之後）**

| 發現 | 處理 | 位置 |
|---|---|---|
| 評分依賴字詞 | 改為依語意評分；S1 第一句接受「妹」或省略主詞 | `fixtures/long-memory.json` |
| 指代無先行詞時幻覺 | 翻譯指示：找不到對象就省略主詞；禁止加入原文沒有的人物、關係、事實 | `src/Translators.js` |
| 綽號被一般化 | 翻譯指示：引號內與作為名稱使用的詞視為專有名詞，漢字保持原樣。沒有引號、需要跨天才知道是名字的情況，留給條件 B | `src/Translators.js` |
| お姉ちゃん被多加 | 翻譯指示：只用來翻譯原文中的 姐姐／姊姊／你／妳，不得自行加入稱呼 | `src/Translators.js` |

這些修改改的是正式版的翻譯指示，因此條件 A 的基準線也會跟著改變。下一次執行（Run 2）以修改後的條件 A 作為新的基準線。

### Run 2：條件 A（修改指示後）— 2026-10-18

平均延遲 981 ms（+164），平均 prompt 508 tokens（+111，指示變長）。自動評分 5/6，人工判讀 4/6。

| 情境 | 原文 | Run 1 | Run 2 | 人工判讀 |
|---|---|---|---|---|
| S1 指代 | 她昨天晚上到了 | 昨日の**お父さん**の夜に着いたよ | 昨日**いた** | ⚠️ 不再編造人物，但「昨晚抵達」被改成「昨天在」 |
| S2 綽號 | 今日も親分いたよ | 今天老大也在喔 | 今天老大也在喔 | ❌ 預期中，需要條件 B |
| S2 綽號 | 親分有沒有變更胖 | お姉ちゃん、おやぶんまた太った？ | 親分、また太った？ | ✅ 不再多加稱呼，名稱保持原樣 |
| S3 約定 | 取れたよ！来週の金曜日 | 搶到啦！下週五 | 預約到囉！下週五 | ✅ |

**觀察**：「不確定時寧可翻得模糊」這句指示被模型理解為可以刪減內容，造成新的錯誤，而自動評分只有 `mustNot`，沒有抓到。

**處理**：指示改為「可以省略未知的指代對象，但其他內容（時間、動作、地點）必須完整翻出」；評分新增 `mustAll`，S1 第一句必須同時保留「夜」與「着」。

### Run 3：條件 A — 2026-10-18

| 情境 | 原文 | Run 1 | Run 2 | Run 3 |
|---|---|---|---|---|
| S1 指代 | 她昨天晚上到了 | 昨日の**お父さん**の夜に着いた | 昨日**いた** | 昨日の**お姉ちゃん**の夜に到着した |
| S4 暗號 | 充電したい… | 想充電… | 想充電... | 想充個電…（語意正確，評分誤判） |

**觀察**：S1 三次三種不同的錯誤。沒有上下文時「她」本來就無法確定，模型（flash-lite）會用不同方式猜。
繼續針對這 6 題修改指示，等於在測試集上調參：每修一題就有另一題換一種方式出錯，指示也越來越長（prompt +111 tokens、延遲 +100～160 ms）。

**決定**

1. 停止為這 6 題調整翻譯指示，保留「不得加入原文沒有的人物、關係、事實」這個原則。
2. S4 評分接受「充個電」。
3. 改為測量變異：執行器新增 `--repeat` 與 `--model`，比較 `gemini-3.5-flash-lite` 與 `gemini-3.6-flash` 各跑 3 次的穩定度。
   若大模型在條件 A 就穩定，S1 的問題主要來自模型能力而非記憶；若仍不穩定，才由條件 B 驗證記憶的效果。

**正式版回歸**：修改後的指示以 30 句日常對話測試（`runDialogueTest`）驗證，30/30，人工檢查語意無退步。

**對 Profile 層的設計含意**：優先記錄「人物與指代對象」（誰要來、誰在哪裡）與「兩人自取的名稱」（綽號、暗號）；計畫類的資訊次之。
